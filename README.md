**“Runaway project”** means a software project that **goes far beyond its planned limits**.

For example:

-  ⏰ Takes much longer than planned 
-  💰 Costs much more than the budget 
-  ❌ Becomes difficult to control/manage 
-  Sometimes fails to deliver the expected software 
So:

>  **35% of computer-based projects are runaway**
 means approximately **35 out of 100 projects** may become significantly **late, over-budget, or difficult to control**.

### Why do we need a structured SDLC?
A structured SDLC gives us a **proper order and plan** for developing software. 

- **Order:** Tells us what to do and when. 
- **Big picture:** Helps us follow all necessary steps. 
- **Avoid mistakes:** Prevents individual decisions from causing overall problems. 
- **Teamwork:** Helps team members coordinate their work. 
- **Track:** Helps monitor **progress and risks** and make changes when needed. 
### ⭐ In one line:
>  **Structured SDLC = proper order + teamwork + tracking + fewer problems.**

### 🟦 High-Level Design (Architecture)
It answers:

>  **“HOW will the whole system be built?”** 

It gives the **big picture** of the system.

Example: For an online shopping system, you decide:

-  There will be a **user module**
- **Payment module**
- **Product module**
- **Database**
-  How these major parts communicate 
You don't worry about exact code yet.

---

### 🟨 Low-Level Design
It answers:

>  **“HOW exactly will each part work?”** 

You go into the **details** of each module.

Example:

-  What classes are needed? 
-  What methods/functions? 
-  How will objects interact? 
-  What design pattern should be used?

They are **similar in the flow**, but **not the same model**.

- **Waterfall:** used to **develop software** step-by-step, with phases largely fixed/frozen. 
- **SMLC:** used to **maintain existing software** and handle new changes/fixes repeatedly. 
**Easy memory:**

>  Waterfall = **Build the software** 🏗️
 SMLC = **Maintain/change the software** 🔧

### When can you use Waterfall?
1. **Short projects** → requirements are already well known. 
2. **Stable product** → product definition is unlikely to change. 
3. **Technology is understood** → the team already knows the technology needed. 
4. **Regulatory requirements** → projects that must follow strict rules/standards. 
5. **Requirements won’t change** → customer requirements are very clear and fixed. 
**Easy exam line:**

>  **Waterfall is best when requirements are clear, stable, and unlikely to change.**

![image.png](https://eraser.imgix.net/workspaces/j7PRLB7uMxm51apemWjs/OjlBWCdDlRWI9XasvFYbqcu7aSX2/image_PBMbk8oM6v8RiaxNLsvlv.png?ixlib=js-3.8.0 "image.png")

### What the slide means
It shows systems such as:

-  ✈️ **Aircraft flight management systems**
-  🏥 **Medical devices**
These systems have **strict regulatory requirements** and need a lot of planning/documentation **up front**.

So their SDLC is likely to have **Waterfall-like parts**:

**Requirements → Design → Implementation → Testing → Delivery**

The important idea is:

>  **Upfront requirements + strict regulations → Waterfall-like development can be suitable.**

### Example where **Waterfall should NOT be used**
Imagine you are building an **Instagram-like social media app** 📱.

Requirements may change often:

-  Users ask for new features. 
-  UI/design changes based on feedback. 
-  Competitors introduce new features. 
-  You may discover problems after users try it. 
Waterfall expects requirements to be **clear and stable**, so frequent changes make it difficult and costly.

👉 In such a case, an **iterative/incremental approach** is more suitable.

![image.png](https://eraser.imgix.net/workspaces/j7PRLB7uMxm51apemWjs/OjlBWCdDlRWI9XasvFYbqcu7aSX2/image_XOgjS37L1Ye0W8dTPguGv.png?ixlib=js-3.8.0 "image.png")

The **V-Model (Verification & Validation Model)** is similar to Waterfall, but its main idea is:

>  **Every development phase has a corresponding testing phase.** 

It is called **V-Model** because the process looks like a **V**.

### Advantages
-  Similar to Waterfall. 
-  Testing activities can be prepared **before formal testing**. 
-  Higher probability of success and better resource usage. 
### Disadvantages
-  No early software prototypes. 
-  If requirements/process change, **test documentation also needs to change**. 
-  Similar limitations to Waterfall. 
### Exam memory 🧠
>  **Waterfall = Development phases in sequence**
 **V-Model = Development phase + corresponding testing phase**

![image.png](https://eraser.imgix.net/workspaces/j7PRLB7uMxm51apemWjs/OjlBWCdDlRWI9XasvFYbqcu7aSX2/image_m_v4Qngf5Br7Ia7mtN1_t.png?ixlib=js-3.8.0 "image.png")

there is a connection, but **Iterative and Incremental are different from Waterfall and V-Model**.

Think of them like this:

- **Waterfall:** ➡️➡️➡️ one phase after another, mostly fixed. 
- **V-Model:** 🔽🔼 development on left + corresponding testing on right. 
- **Iterative:** 🔄 repeat and **improve/refine** what you already built. 
- **Incremental:** ➕ build and **add new parts** one by one.

## 🌀 Spiral Model — Simple Explanation
The **Spiral Model** was proposed by **Boehm**.

Instead of developing software in one straight sequence like Waterfall:

**Requirements → Design → Coding → Testing**

the Spiral Model develops software through **repeated loops (spirals)**.

### What does each loop mean?
👉 **Each loop = one phase/cycle of the software process.**

For example:

**1st loop:** System feasibility
 ↓
 **2nd loop:** Requirements definition
 ↓
 **3rd loop:** System design
 ↓
 **4th loop:** Further development, etc.

So, as the spiral moves outward, the software development progresses through more detailed/larger activities.

### 🧠 Easy memory
>  **Waterfall = straight line ➡️**
 **Spiral = repeated loops 🌀**
 **Each loop = a phase of the process.**
